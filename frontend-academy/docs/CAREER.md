# Подготовка к первой frontend-работе

Рабочая цель — собрать проверяемые доказательства компетентности и научиться применять их на новой задаче. Основной frontend checkpoint находится в конце этапа L, урок 193, перед backend-путём M. Искать подходящие стажировки и вакансии можно раньше по результатам конкретной практики: количество пройденных уроков не гарантирует должность или предложение о работе.

В этой версии ориентиром служит список требований ученика. Реальная вакансия ещё не предоставлена, поэтому сведения о работодателе, рынке, зарплате и обязательности отдельных технологий не выдуманы. При получении вакансии матрица ниже заполняется по её актуальному тексту.

## Портфолио как доказательство

После G выбрать два самостоятельных React-приложения с различными задачами. После H/I и J/K/L добавить сильный проект: административную панель, real-time интерфейс либо Next.js-приложение. Не требуется публиковать двенадцать одинаково слабых демонстраций: проект должен позволять оценить собственный вклад.

У каждого выбранного проекта должны быть:

- понятная пользовательская задача и работающая демоверсия либо воспроизводимый локальный запуск;
- README с командами, архитектурой, ограничениями и реально выполненными проверками;
- история осмысленных commits и хотя бы один PR с обсуждением и исправлениями;
- сценарий загрузки, пустого состояния и ошибки, если проект использует API;
- конкретный тест, ошибка или измерение, по которым видно инженерную работу;
- собственное объяснение решений и небольшое изменение без готового кода.

Отдельно обозначать учебный проект, проект для знакомого заказчика, оплаченный фриланс, стажировку и официальную занятость. Сайт кафе может стать доказательством работы с требованиями после согласия владельца; сам факт его создания не является коммерческим стажем. Помощь AI, подсказки и совместная работа описываются честно.

## Тематические треки интервью

Треки открываются после соответствующих тем программы. Они не являются требованием изучить всё до урока 9. При текущем занятии проверяются функции и известные конструкции, а не Hooks или backend.

| Трек | Когда | Задание или вопрос | Что оценивается |
| --- | --- | --- | --- |
| JavaScript | A | Сгруппировать записи по условию, найти пропуск, объяснить изменение объекта и написать функцию с ясным контрактом | Функции, массивы, строки, объекты, циклы, неизменяемость, крайние случаи |
| Асинхронность | C/D | Предсказать порядок вывода с Promise и таймером; устранить устаревший ответ поиска | Event loop, microtasks/macrotasks, async/await, ошибки и отмена |
| TypeScript | E | Описать несколько состояний запроса и безопасно обработать неизвестный ответ API | Union, narrowing, generics по потребности, различие типов и runtime-проверки |
| HTML/CSS | B/C | Сверстать новый блок по макету, объяснить layout, исправить перекрытие и проверить клавиатуру | Семантика, каскад, специфичность, Flexbox/Grid, адаптивность, доступность |
| React | G/H | Дополнить форму, устранить лишний state или неверный эффект, объяснить повторный рендер | Props, state, Hooks, Context, ключи, зависимости, cleanup и границы компонентов |
| HTTP/API/WebSocket | D/H | Разобрать неуспешный запрос и восстановить список после разрыва real-time связи | Статусы, заголовки, CORS, REST, повторы, reconnect, согласованность |
| Git и команда | F/L | Создать ветку, оформить PR, разрешить конфликт и объяснить выбор merge/rebase | Команды с пониманием последствий, commits, коммуникация, ревью |
| Debugging и тестирование | C/K | Воспроизвести баг, найти причину в DevTools, написать проверку поведения | Гипотезы, инструменты, минимальный пример, unit/integration/E2E |
| Архитектура и code review | H/J | Разделить ответственность формы, API и таблицы; отрецензировать небольшой чужой фрагмент | Поток данных, границы модулей, корректность, компромиссы, приоритет замечаний |
| Проекты и поведение | G–L | Объяснить сложное решение, ошибку, получение обратной связи и изменение требований | Собственный вклад, ясность, честность, взаимодействие и выводы |

Примеры вопросов без готовых ответов:

1. Чем возвращаемое значение функции отличается от вывода сообщения? Как это проверить вызывающим кодом?
2. Почему изменение вложенного объекта может затронуть другой участок приложения? Как уточнить контракт копирования?
3. Что произойдёт, если два ответа поиска придут в обратном порядке? Как воспроизвести это до исправления?
4. Почему тип TypeScript не доказывает, что внешний JSON соответствует контракту?
5. Как определить владельца состояния формы и отличить его от серверных данных?
6. Когда эффект React нужен, а когда вычисление можно выполнить при рендере?
7. Какие действия предпринять, если у всех запросов к API внезапно появилась ошибка?
8. Что должен сделать WebSocket-клиент после потери части событий?
9. Как убедиться, что оптимизация действительно помогла пользователю?
10. Какое замечание ревью обязательно исправить, а какое является обсуждением стиля?

В live coding сначала уточнить входы, ожидаемый выход и ограничения, назвать план, реализовать минимальный работающий вариант и проверить его. Молчаливая быстрая печать не является отдельным признаком качества. Если не хватает времени, описать невыполненную часть и способ её проверки, не объявляя задачу завершённой.

## Пробное интервью

Первую репетицию провести после подтверждённого G; полную — после L. Для текущего уровня доступны короткие репетиции на 10–15 минут по одной изученной теме.

Пример полной сессии на 75–90 минут:

1. 10 минут: рассказ о проекте и собственном вкладе.
2. 20 минут: задача JavaScript/TypeScript с объяснением и проверкой границ.
3. 20 минут: небольшой React-сценарий или debugging интерфейса.
4. 15 минут: HTTP/асинхронность и архитектурный компромисс.
5. 10 минут: code review, Git-сценарий и поведенческий вопрос.
6. До 15 минут: обратная связь и план устранения двух главных пробелов.

До сессии согласовать разрешённые материалы. При проверке самостоятельности не использовать готовый ответ AI. Обычная документация может быть разрешена, если проверяется рабочее решение, а не запоминание синтаксиса.

Для каждой категории применяются уровни 0–4: 0 — нет результата или доказательства, 1 — знакомство, 2 — базовое понимание, 3 — самостоятельное применение, 4 — уверенное применение с объяснёнными компромиссами.

| Категория | Наблюдаемый результат |
| --- | --- |
| Корректность | Решение соответствует контракту и не скрывает известную ошибку |
| Объяснение | Логика, поток данных и результат объяснены понятными словами |
| Самостоятельность | Новое условие решается без готового алгоритма |
| Проверка и debugging | Ожидаемые результаты заданы, края проверены, причина бага найдена |
| Инженерные решения | Ответственность разделена, выбор обоснован, ограничение названо |
| Коммуникация и ревью | Вопросы уточняют задачу, замечания конкретны, обратная связь используется |

Локальный ориентир успешной репетиции — 18 из 24 баллов, не ниже 3 по корректности, объяснению и самостоятельности, не ниже 2 по остальным категориям. Это правило учебной репетиции, а не универсальный порог работодателей. Средний балл не отменяет критическую ошибку или отсутствие обязательного навыка вакансии.

После интервью сохранить дату, задания, наблюдаемые доказательства по каждой категории, две сильные стороны, два главных пробела и адресную практику. Повтор проводить на новом условии после исправлений; не заучивать прежний ответ.

## Frontend checkpoint перед backend

На уроке 193 проверить готовность по доказательствам:

1. JavaScript и TypeScript: новая задача с объяснением, границами и отладкой без готового решения.
2. HTML/CSS: адаптивная доступная вёрстка, понимание каскада, layout и клавиатурного сценария.
3. React: два самостоятельных приложения; объяснение props, state, Hooks, Context и повторного рендеринга.
4. Сеть: API со всеми состояниями, отменой/конфликтом; real-time восстановление при наличии такого требования.
5. Инженерная работа: критические тесты, измеренная оптимизация, Git/PR/конфликт, содержательный code review и README.
6. Проект: архитектурная защита и новое небольшое изменение требования без готового кода.
7. Собеседование: пробная сессия с разбором, матрица подходящей вакансии и план устранения обязательных пробелов.

Если один обязательный фундаментальный пункт не подтверждён, продолжить адресную frontend-практику до M, вместо расширения стека. Backend-темы не должны служить способом избежать пробела в функциях, состоянии или сети.

Для отклика собрать короткое резюме с фактическими навыками, две-три сильные работы, ссылки на код и проверенную демоверсию. Подготовить рассказ на две минуты: задача, собственный вклад, трудная ошибка, принятое решение и результат проверки. Фактический опыт описывать без повышения его статуса. Решение о найме зависит от требований конкретной роли и результатов её отбора.
